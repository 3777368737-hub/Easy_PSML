# 批量生成 PS 与 ML：实现步骤与原因

## 使用方法

1. 在“装配工作台”中创建人物背景、申请项目并挖掘绑定故事，或使用背景信息页的兼容入口。也可以直接通过顶部导航进入 `/batch`。
2. 添加任意数量的方向。每个方向填写学校、项目名称 / 专业方向，可粘贴官网资料。
3. 选择一个背景实例；每个方向可以额外选择一个或多个已完成故事实例。每个方向默认同时生成 PS（Personal Statement）和 ML（Motivation Letter），也可只勾选一种。分别填写题目、具体要求和 100～5000 词的目标字数。
4. 点击“开始批量生成”。页面显示逐篇进度；同一浏览器刷新或重新打开页面可查看保存的批次。
5. 完成后可预览、单篇下载 TXT、将已完成文书合并下载为 Markdown，或进入原结果页查看中文大纲、审核及修改英文草稿。部分失败时点击“仅重试失败项”。

批量模式可以只依据背景实例生成，也可以复用已经完成的故事实例。选择故事时，故事素材会和分析、大纲一起提供给模型；没有选择故事时只使用完整背景资料。提供的事实越具体，初稿越有依据；请核对最终内容。

## 第一步：分清共享资料与每篇文书的要求

`frontend/lib/types.ts` 与 `backend/app/schemas.py` 定义一致的批量请求。新请求引用一个 `background_instance_id`，同时兼容只传旧 `profile_id` 的请求。一个批次包含多个方向，每个方向包含 1～2 种文书，并可引用多个已完成故事实例。方向内的学校、项目和官网资料共享；PS、ML 的题目和字数分别设置。

原因：个人经历不用反复录入，而文书要求必须独立。将两类文书拆为任务后，才不会将 PS 的字数或题目错误用于 ML。前后端都校验数量、空白输入、字数、重复文书类型，错误会在调用模型之前暴露。

## 第二步：复用已验证的生成流程

`backend/app/services/batch.py` 在旧兼容模式下为每篇文书建立独立分析和会话；在实例模式下为每篇文书创建 `EssayProject`，引用所选背景和故事，再调用实例领域工作流。两种模式都不会共享草稿状态，也不会伪造访谈回答。

```mermaid
flowchart LR
  A[录入一次个人资料] --> B[多个方向 × PS / ML]
  B --> C[每篇独立分析项目]
  C --> D[中文大纲]
  D --> E[英文草稿]
  E --> F[预览 / 下载 / 继续修改]
```

原因：沿用现有的模型输出校验、版本保存和修改流程，避免维护两套生成逻辑。提示词分别强调 PS 的经历与成长，以及 ML 的申请动机、项目匹配和计划；当前方向优先于个人画像里的概括性目标方向。只能使用提供的事实。

## 第三步：用持久化后台任务承接长时间生成

`backend/app/services/store.py` 自动创建 `batches` 和 `batch_items` 表，保留原有数据库。创建接口返回 `202` 与批次编号，FastAPI 生命周期中的后台 worker 逐篇执行，前端轮询进度。

- 批次状态：`pending`、`running`、`completed`、`partial_failed`、`failed`。
- 每篇任务分别记录状态、生成阶段、分析编号或文书项目编号、会话编号和安全错误信息。
- 每阶段前检查模型请求限额，同一浏览器身份同时只允许一个活动批次。
- 同一 `request_id` 和同一请求内容会返回原批次；复用编号但修改内容会被拒绝。

原因：多篇文书可能耗时数分钟，一个长 HTTP 请求容易超时。任务保存在 SQLite 后，关闭页面不会中断后台生成；唯一请求编号可防止网络中断后的重复提交。

## 第四步：保留成功结果并从检查点重试

一篇失败后继续处理其他文书，重试接口只将失败任务重新排队。已经保存的分析、大纲或草稿会被复用，已完成的文书保持原样。后端重启时恢复未完成任务；实例模式从 `EssayProject.current_step` 和版本记录恢复，旧模式从会话版本记录恢复。

原因：一个方向失败不应该浪费其他方向的成果，也不应该重复付出已完成步骤的模型调用成本。清空历史会级联清除批量记录，正在执行的任务也不会重新创建已删除的资料。

## 第五步：接入操作入口、结果页与验证

`frontend/app/batch/page.tsx` 提供方向增删、各篇要求、进度、历史批次、失败重试和下载。表单按个人画像关联保存，新的画像会清理旧表单。活动任务独立于当前查看的历史批次轮询，避免查看旧文书时遗漏新任务进度。

`backend/tests/test_batch.py` 使用模拟模型与临时数据库测试完整流程，覆盖多个方向的上下文隔离、不同文书类型与字数、部分失败、幂等提交、权限隔离、重启恢复、产物写入中断、后台生命周期及删除中的任务。原单次流程的测试一并执行；前端执行 lint、TypeScript 类型检查和生产构建。

## API

| 方法 | 路径 | 用途 |
| --- | --- | --- |
| POST | `/api/batches` | 创建批次，返回 202；新请求包含 `background_instance_id`、`request_id`、`tone`、`directions`，每个方向可带 `story_instance_ids`；旧 `profile_id` 继续兼容 |
| GET | `/api/batches` | 当前浏览器身份的最近批次 |
| GET | `/api/batches/{id}` | 批次详情、逐篇进度与草稿 |
| POST | `/api/batches/{id}/retry` | 仅重新排队失败项，返回 202 |

所有接口沿用 `X-Client-Id` 归属校验。旧模式结果继续出现在 `/api/history`；实例模式结果出现在 `GET /api/workspace` 的 `projects` 中，也可通过 `/api/essay-projects/{id}` 打开。批量页面通过“刷新任务”读取最新草稿。

## 当前运行边界

当前 worker 按单个 FastAPI 进程运行，启动时不要配置多个 Uvicorn workers。任务数量不设产品层固定上限，后台全局逐篇执行，适合当前 SQLite MVP；若需要多人高并发，可将任务调度替换为独立队列 worker。

已保存阶段可恢复；进程在模型请求返回并保存之前中断时，该次请求可能在重启后再次调用。模型限流或服务错误会作为单篇失败显示，等待限额恢复后可重试。目标字数由现有生成流程约束，实际词数在预览处展示，仍应按学校要求核对。
